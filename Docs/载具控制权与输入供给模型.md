# 载具控制权与输入供给模型：本地控制判定与自主行驶的前提

> [!IMPORTANT]
> 载具模拟完全由 **输入（Input）** 驱动；在 **网络物理预测（Network Physics Prediction）** 启用时，本机输入**只有在载具被判定为 **本地控制（Locally Controlled）** 时才会进入模拟**，否则会被 **模拟状态（Simulated State）** 反向覆盖并清零。该判定默认绑定在「本地玩家 **控制器（Controller）** **Possess（占领）** 的 **Pawn（傀儡体）**」这一形态上，因此以普通 **Actor（实体）** 承载载具、由外部组件写入输入、或无人驾驶的场景都会被判为非本地控制——这既是「Actor 载具无法控制」的成因，也是「载具不能自发行驶、必须玩家控制」的同一根源。

## 1. 模型前提

**单刚体（Single Rigid Body）** + **解析力模型（Analytical Force Model）** 的载具模拟，其输入端具备三个固有属性：

1. **输入驱动**：悬挂力、轮胎纵向/侧向力、驱动力矩等全部由**控制量（Control Value）**（油门、转向、制动、离合、手刹等）经解析公式求得；控制量为零时，力恒为零。
2. **线程分离**：模拟运行在 **物理线程（Physics Thread，PT）**，而输入产生于 **游戏线程（Game Thread，GT）**；二者按各自的节拍运行，需要通过显式通道传递。
3. **每步供给**：输入不是一次性事件，而是**每个物理子步（Physics Substep）**都要供给的一份状态；缺一步，该步内所有力为零。

由第 1、3 条可推出一个关键结论：**载具不会「记住」上一次的输入来自行前进，也不会在没有输入时自行产生运动。** 静止载具的唯一原因，是它当前收到的输入为零。

## 2. 输入供给链

输入从产生到作用于刚体，是一条定序的链：

```
[输入源 Input Producer]
      │  产出本物理步的控制量（油门 / 转向 / 制动 / …）
      ▼
[输入容器 Input Container]        ← 缓冲与合并：GT 频率 → PT 频率
      │  跨线程拷贝（本机 → 物理线程）
      ▼
[物理线程 Physics Thread]
      │  各模拟模块按名称读取控制量
      ▼
[解析力 Analytical Force] → [单刚体 Single Rigid Body]
```

链上任一环节缺失或归零，下游即为零输出：

| 环节 | 缺失或归零的结果 |
|---|---|
| 输入源 | 无控制量产出 → 恒为零 |
| 输入容器 | 控制量无处承载 → 恒为零 |
| 跨线程拷贝 | 物理线程读不到本机输入 → 恒为零 |
| 本地控制判定（见第 3 节） | 本机输入被覆盖 → 恒为零 |

前三个环节是**数据通路**问题；第四个环节是**控制权归属**问题，也是本篇的核心。

## 3. 控制权归属与输入分流

当 **网络物理预测** 启用时，同一份载具模拟可能同时存在于多个端（权威端与本机预测端），系统必须回答一个前置问题：**本机此刻产出的输入，是否有权作用于这次模拟？**

- 若有权（本机玩家正在驾驶这辆车）→ 本机输入是模拟的**来源**；
- 若无权（本车由远端操控，本机只是在预测/复现）→ 模拟的输入**来自网络**，本机不得用自己的输入覆盖它。

物理线程因此在**每个物理步开始时**做一次分流：

```
        ┌────────────────────────────┐
        │ 本载具是「本地控制」吗？    │
        └─────────────┬──────────────┘
              是 │                 │ 否
                 ▼                 ▼
   本机输入 → 模拟输入状态     模拟输入状态 → 本机输入容器
   （模拟采用本机输入）        （本机输入被覆盖清零）
```

分流规则的两条分支是对称的：

1. **本地控制**：把本机输入写入「模拟的输入状态」，供模拟使用与后续上报；本机输入容器保持有效 → 载具响应操作。
2. **非本地控制**：把「模拟的输入状态」反向写回本机输入容器 → **本机输入被清零**。

关键事实：**「模拟的输入状态」在其初始状态下是空的，且只会在「本地控制」分支或收到网络输入时被填充。** 因此对于一辆从未被任何端操控过的载具，若被误判为非本地控制，它的输入容器会被这份空状态反复覆盖，结果恒为零——即便玩家正在操作，载具也纹丝不动。

## 4. 本地控制的判定依据

「本地控制」不是由输入本身决定的，而是由**载具与本地玩家的关系**推导出来的。默认判定沿一条依赖链执行，任一步不满足即判为非本地控制：

```
Owner（载具实体）
 ├─ 有 控制器（Controller）吗？
 │     否 ─────────────────────────────────► 非本地控制
 │     是
 ├─ 该实体是 Pawn 吗？
 │     否 ─────────────────────────────────► 非本地控制
 │     是
 └─ 其控制器是「本机玩家控制器」吗？
       否 ─────────────────────────────────► 非本地控制
       是 ─────────────────────────────────► 本地控制
```

这条链的实质是：**判定对象是「被本地玩家控制器 Possess 的 Pawn」这一角色关系，而不是「谁在写输入」。**

由此产生一个结构性错位：

- 「谁是本地控制」由**引擎的角色系统**（网络角色、控制器、Possess）回答；
- 「谁在产生输入」由**输入源**回答。

系统**默认假定二者重合**——即：驾驶这辆车的人，就是本机被 Possess 的玩家。一旦这个假定不成立（载具是普通 Actor、无控制器、或由外部组件代写输入），判定链在第一步或第二步即失败，控制权被判给「远端」，本机输入随之被清零。

## 5. 两条限制的成因

### 5.1 限制一：以 Actor 承载的载具无法控制

| 步骤 | 以 Pawn 承载 | 以普通 Actor 承载 |
|---|---|---|
| 是否有控制器 | 有（玩家 Possess） | 无（或不由玩家直接控制） |
| 是否 Pawn | 是 | 否 |
| 本地控制判定 | 本地 | **非本地** |
| 输入分流 | 本机输入进入模拟 | **本机输入被覆盖清零** |
| 结果 | 可控制 | 无法控制 |

差别不在输入通路（两者都能把控制量写进输入容器），而在**控制权判定**：Actor 形态在判定链上天然不满足条件，于是即便输入源正常产出、容器正常承载，物理线程仍会把这份输入视为「无权输入」而丢弃。

### 5.2 限制二：载具不能自发行驶，必须玩家控制

自主行驶（**Autonomous Driving**）要求「模拟持续收到非零输入」。而输入供给链（第 2 节）的唯一默认输入源是**本地玩家控制器**。其直接后果：

1. **无玩家即无输入**：没有玩家控制器持续产出控制量时，输入恒为零，无论载具形态如何，解析力恒为零，载具静止。
2. **自主行为不属于玩家输入通路**：官方模型没有内置「由 AI、脚本或巡航逻辑产生输入」的默认路径；这类输入不是「玩家控制」，因此走玩家通路会被第 3 节的判定拦截。
3. **控制权与输入源被绑定**：由于第 4 节的判定假定「驾驶者即本地玩家」，任何不由本地玩家产生、却要作用于本机模拟的输入，都缺少一条合法的注入路径。

### 5.3 两条限制的同一根源

```
              ┌────────────────────────────────────────┐
              │ 判定与控制权绑定于：                    │
              │ 「本地玩家控制器 Possess 的 Pawn」      │
              └───────────────────┬────────────────────┘
                      ┌───────────┴───────────┐
                      ▼                       ▼
           以 Actor 承载载具             无玩家 / 无控制器
           → 判定为非本地                → 无输入源
           → 本机输入被清零              → 输入恒为零
           → 无法控制                    → 不能自发行驶
```

两条限制并非彼此独立，而是同一绑定的两个投影：**「谁有权控制」与「谁来供给输入」被合并成了一个条件。** 一旦载具形态（Pawn/Actor）或操作者（玩家/非玩家）偏离该条件，其中一侧即失效。

## 6. 突破的原则

问题的本质是**两处耦合**：控制权判定耦合于引擎的角色系统，输入供给耦合于玩家控制器。解开这两处耦合，即可同时消除两条限制。

### 6.1 显式声明控制权

不应完全依赖引擎的隐式角色推导，而应允许载具**主动声明「我是本地控制」**：

- 声明在有明确「本机玩家正在操作此载具」的时机写入（例如玩家进入/接管载具）；
- 声明必须**优先于**隐式推导生效；
- 必须保留一条**防误标守卫**：远端同步而来的载具（**Simulated Proxy（模拟代理）**）的输入来自网络，无论声明如何都不得判为本地，否则会被本机输入污染模拟。

显式声明使「以 Actor 承载、由外部组件写入输入」的形态重新获得控制权，而无需把载具强行改成 Pawn。

### 6.2 解耦输入供给与控制主体

输入源应可插拔，与控制权归属、载具形态相互独立：

- 同一套模拟，输入可来自玩家、AI、脚本或回放；
- 自主行驶（AI/巡航）作为一种**与非玩家控制主体配套的输入源**存在，其合法性由第 6.1 节的显式声明保证，而不是被角色系统拦截。

### 6.3 两者的关系

```
控制权声明（6.1） ── 决定「本机输入是否有权进入模拟」
        │
        └── 输入源（6.2） ── 决定「输入是什么、由谁产生」
                 │
                 ▼
        输入 → 分流判定（本地？）──► 模拟 → 解析力 → 单刚体
```

只有当**控制权声明成立**且**存在有效输入源**时，模拟才会持续收到非零输入。二者缺一：

- 有输入源、无控制权 → 输入被清零（限制一）；
- 有控制权、无输入源 → 输入恒为零（限制二）。

## 7. 现象清单（诊断信号）

| 现象 | 指向 |
|---|---|
| 输入容器在游戏线程可见非零值，物理线程读到的却恒为零 | 控制权被判为非本地，输入被模拟状态覆盖（第 3 节） |
| 输入源与容器均正常，载具仍不动 | 同上，问题在控制权判定而非数据通路 |
| 换成 Pawn + 玩家 Possess 后即可控制 | 判定链依赖「Pawn + 控制器」，Actor 形态不满足（第 4 节） |
| 玩家不操作时载具绝不自发移动 | 无独立输入源；输入供给耦合于玩家控制器（第 5.2 节） |
| 只有在启用了网络物理预测后才出现 | 分流逻辑（第 3 节）仅在预测启用时生效 |
| 远端同步来的载具反而能正确复现运动 | 非本地分支对远端载具是正确的；错的是把本机载具也判成了非本地 |

## 8. 检查清单

1. 本机输入是否确实到达了输入容器？若到达而载具不动，则问题在控制权判定。
2. 载具的拥有者是否为被本地玩家控制器 Possess 的 Pawn？若否，判定链是否在第一步或第二步即失败？
3. 是否存在一条**显式控制权声明**，且其优先级高于隐式推导？
4. 显式声明是否带有防止 **Simulated Proxy** 误标本地的守卫？
5. 是否存在**独立于玩家控制器**的输入源，以供自主行驶使用？
6. 「本机输入被清零」与「本机无输入」是否被区分开？前者是控制权问题，后者是输入源问题。
